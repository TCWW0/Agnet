## 一、纯核心与效果边界

### 决策 1：系统提示由宿主注入，而不是在 `update()` 里构建

**问题**：系统提示需要携带工作目录、记忆条目、skill 目录 —— 全都要读文件系统。
但 `update(Model, Msg) → Step{Model, Cmd}` 是纯函数，`make_request()` 在它里面。

**选项**

- A `update()` 直接读文件填好 `system_prompt`。最直观。
- B 把整个提示当成 `Model` 的一个字段，提交时由前端填。
- C `make_request()` 留空，由 `AsyncHost::execute_cmd(StartStream)` 用注入的
  `SystemPromptProvider = std::function<std::string()>` 补上。

**选择 C。理由**：A 会让 `update()` 变得不可确定性测试 —— 一旦碰 IO，
`headless_runner_test` 就必须准备文件系统夹具，而那套测试的全部价值就在于
「同样的输入必然得到同样的输出」。B 看起来干净，但 `Model` 会因为提示内容变化
而在每轮都不同，快照比较失去意义，且前端要重复知道提示怎么拼。

C 把 IO 留在唯一已经允许做 IO 的地方（effect 解释层），核心保持纯。

**代价**：`Request` 多一个字段，多一个注入点要接线。这个代价很小，而且换来一个
关键收益 —— provider 是**函数**而不是字符串，所以 `remember` 刚写下的事实下一轮
就出现在提示里，不需要任何显式刷新。

```cpp
// async_host.cpp
// update() 是纯的，make_request() 只能把 system_prompt 留空。在这里补上：
if (system_prompt_provider_) {
    command.request.system_prompt = system_prompt_provider_();
}
```

**可迁移的一般原则**：需要 IO 的数据不要往纯函数里塞，也不要塞进状态；
把它做成**在效果边界求值的函数**。副产品是「每次求值都拿到最新值」这一语义免费到手。

### 决策 2：`Request` 新增字段用默认值，而不是改所有构造点

**问题**：`Request` 加 `system_prompt` 会影响既有的 36 个测试。

**选项**

- A 改所有构造点，显式传空串。
- B 新字段给默认值（`std::string` 默认 `""`），既有 designated initializer 不动。

**选择 B**。既有测试全部用 designated initializer 写的，新字段缺省即空，
`HeadlessRunner` 与它的测试**零改动** —— 这是硬不变量之一。

**可迁移的一般原则**：给聚合体加字段时，先确认既有构造点用的是
designated initializer 还是位置初始化。前者可以无痛加字段，后者不能。
这条约束值得在早期就定下来。

## 二、并发与生命周期

### 决策 3：`phase` 就是 in-flight 计数器，但要靠一条边界保证兜住

**问题**：`run_until_quiescent()` 要判断「还有后台任务在飞吗」。

**选项**

- A 维护一个 `in_flight_` 计数器，post 前 ++，终态 --。
- B 直接看 `phase`：`Streaming`/`ExecutingTool` 说明有 worker 在飞，
  `Idle`/`AwaitingPermission` 说明没有。

**选择 B。理由**：计数器是**冗余状态**，一旦与 `phase` 不一致就是最难查的 bug 类型。
`phase` 本身已经完整表达了这个信息。

**代价（关键）**：B 依赖一条边界保证 —— **每个 stream 必须恰好投递一个终态事件**。
provider 抛异常、或者静默返回什么都不发，`phase` 会永远停在 `Streaming`，
`wait()` 永久挂死。

不能用超时兜（超时会让测试 flaky），所以在 worker 包装层强制：

```cpp
bool terminal_posted = false;   // worker 内单线程，无需同步

EventSink sink = [inbox, token, &terminal_posted](Msg msg) {
    if (std::holds_alternative<StreamFinished>(msg)
        || std::holds_alternative<StreamError>(msg)) {
        terminal_posted = true;
    }
    if (token.stop_requested()) return;
    inbox->post(std::move(msg));
};

try { stream(std::move(request), sink); }
catch (const std::exception& e) { sink(Msg{StreamError{.message = e.what()}}); }
catch (...) { sink(Msg{StreamError{.message = "unknown stream failure"}}); }

if (!terminal_posted) {
    sink(Msg{StreamError{...}});   // 静默返回也被合成一个终态
}
```

**可迁移的一般原则**：用既有状态代替冗余计数器，前提是**把它依赖的不变量显式
强制出来**，而不是写在注释里指望调用方遵守。「这个契约靠谁保证」必须有答案，
且答案不能是「大家小心一点」。

### 决策 4：先 drain 再 wait，唤醒用电平语义

**问题**：owner 线程阻塞等待后台消息，怎么保证不丢唤醒也不挂死。

**选择**：循环写成 `stop 检查 → drain_inbox() → 静止判定 → wait()`。

**理由**：唤醒是**合并**的（N 条消息只需要一次唤醒，因为 `drain_inbox()`
一次 swap 走整批）。如果先 wait 再 drain，「消息已在 Inbox 但唤醒已被消费」
这个窗口会挂死。先 drain 消除了这个窗口。

**可迁移的一般原则**：合并型唤醒（coalescing wake）必须配「先检查后等待」的循环
结构。反过来写在低负载下也能跑，只在竞态窗口命中时挂死 —— 属于最难复现的一类 bug。

### 决策 5：`WakeSignal` 用 mutex + condvar，而不是计划里的 `binary_semaphore`

**这是一次计划被实现推翻的记录。**

原计划写的是 `std::binary_semaphore sem_{0}`，理由是「多次 signal 合并成一次唤醒
是正确的」。语义判断没错，但实现选错了：`binary_semaphore` 在已置起时再
`release()` 会突破 `max() == 1`，那是**未定义行为** —— 而「已经置起时再 signal」
恰好是这里的常态（多个 worker 背靠背 post）。

改成 mutex + condvar + `bool signaled_`，语义完全一样（电平而非边沿，标志会保持
置起所以不丢唤醒），且没有 UB。

**可迁移的一般原则**：选并发原语时，先确认**你的常态调用序列**在该原语的定义域内。
「语义对得上」不等于「用法合法」。计划阶段的原语选择要在实现时复核一遍。

### 决策 6：`task_isolated` 用 detach，不 join

**问题**：工具执行放在独立线程上（与 provider 共享池分离）。析构时要不要 join？

**选项**

- A join，保证没有线程活得比池久。教科书答案。
- B detach，不等。

**选择 B。理由**：隔离通道**存在的意义**就是任务可能永久 wedge（卡死的 NFS read、
不响应的子进程）。析构时 join 会让 `~AsyncHost` 永久挂死 —— 那正好毁掉隔离的目的。
选 A 等于用一个更糟的失败模式（整个程序挂死）替换一个可控的失败模式（一个线程泄漏）。

**代价**：detached 线程可能在宿主析构后还活着，所以它捕获的状态必须活得比宿主久。
用 `shared_ptr<InboxState>` 和 `shared_ptr<WakeSignal>` 解决：线程持有副本，
post 前查 `stop_token` 直接丢弃结果。无泄漏、无悬垂、无挂死。

`pthread_create` 返回 EAGAIN 时退化到共享池而不是丢掉工作 —— 最坏表现为排队，
严格优于丢弃。

**可迁移的一般原则**：「不泄漏资源」不是最高优先级的目标。当严格清理会导致
**更严重**的失败模式时，选可控的泄漏，并用共享所有权把悬垂风险消掉。
先问「这两种失败哪个更糟」，再决定。

### 决策 7：`workers_.reserve(max)` 是正确性要求，不是性能优化

`worker_loop` 持有 `this`，而 `task()` 里的 `emplace_back` 一旦触发 realloc，
已有 worker 持有的指针就失效。构造函数里 `reserve(max_workers_)` 保证永不 realloc。

**可迁移的一般原则**：容器里的对象如果被外部持有指针/引用，`reserve` 从性能优化
升级成正确性前提。这类约束必须写进注释，否则日后有人「顺手清理」掉它。

## 三、Provider 抽象

### 决策 8：先接 Ollama，不是先接 Anthropic

**问题**：三个 provider 先做哪个。

**选择 Ollama。理由**（这是抓包核实过的，不是猜的）：Ollama 的 NDJSON 里
**工具调用单帧原子到达，`arguments` 已经是 JSON object**：

```json
{"message":{"content":"","tool_calls":[{"id":"call_mxz4bkt2",
 "function":{"index":0,"name":"calculator","arguments":{"a":6,"b":7}}}]},"done":false}
```

这与既有的 `StreamToolCall{id, name, args}` **1:1 对应**，不需要任何 delta 累积。
所以第一个 provider 可以只解决「HTTP 流式 + 行分帧 + Msg 映射」，
把「跨帧累积」这个独立难点留到第二个 provider。

而且本地跑，免费、无速率限制、可以随便重试。

**代价**：先做简单的那个，意味着第二个 provider 会暴露出第一个没有覆盖到的抽象
不足。这是**预期内**的代价，而不是失误 —— 反过来先做 SSE 累积那个，
第一次 tracer bullet 就要同时验证四件事，失败时无从定位。

**可迁移的一般原则**：多个同类适配器，先做**能力最原子、反馈最快**的那个跑通
端到端，再用第二个去检验抽象。不要为了「先做最难的」而让第一颗子弹背上四个未知。

### 决策 9：跨帧累积完全关在传输层内，`StreamToolCall` 契约不变

**问题**：Anthropic 和 OpenAI 的工具参数是**逐字符流式**的。要不要在 `Msg` 里
加一个 `StreamToolCallDelta` 变体？

**选项**

- A 加 delta 变体，让 Core 负责拼装。
- B 累积状态留在传输层，只在参数完整时发出**一个** `StreamToolCall`。

**选择 B。理由**：加 delta 变体会让 `update()` 承担「拼 JSON 字符串」的职责，
而那是纯粹的 wire 格式细节。更糟的是 Ollama 根本没有 delta —— Core 会为了
迁就两个 provider 而变得比任一个都复杂。

B 让 `StreamToolCall` 保持「一次调用，一个事件」的语义，Core 与 host 对
provider 差异完全无知。

**代价**：每个 SSE provider 要自己维护累积状态。这个代价是**局部**的，
且两者的累积逻辑差异恰好证明了不该上移（见下一条）。

**可迁移的一般原则**：适配器之间的差异，要在**最靠外的那一层**吸收掉。
让核心去迁就多个外部格式，结果是核心比任何一个外部格式都复杂。

### 决策 10：OpenAI 用 `std::map<int, ToolAccumulator>`，Anthropic 用单组字段

**这是两者的本质差异，也是最值得记住的一条。**

| | Anthropic | OpenAI |
|---|---|---|
| 块结束事件 | 有：`content_block_stop` | **没有** |
| 并发工具调用 | 一次只开一个块 | 可**交错**，靠 `index` 区分 |
| 发出时机 | `content_block_stop`，明确 | 只能等 `finish_reason` |
| 累积状态 | 单组字段够了 | 必须 `map<int, ...>` |

Anthropic 有明确的块结束信号，所以 `in_tool_block_` + 三个字段就够。
OpenAI 没有块结束事件，且允许多个工具调用交错到达，所以必须按 `index` 分桶，
在 `finish_reason` 到达时统一 flush。

用 `std::map` 而不是 `unordered_map`：**按 index 有序发出，工具调用顺序才是确定的**。
无序容器会让同样的输入产生不同的发出顺序，测试变 flaky，行为不可复现。

**可迁移的一般原则**：需要确定性输出时用有序容器，哪怕查找稍慢。
「反正会全部遍历一遍」不是用 `unordered_map` 的理由 —— 遍历顺序本身就是输出的一部分。

### 决策 11：三处请求序列化差异，如实各写一遍

三个 provider 在三个维度上都不一样，没有任何一处可以共享：

| | 系统提示 | 工具 schema | 结果关联 |
|---|---|---|---|
| Ollama | messages 首元素 | `function.parameters` | `tool_name` |
| Anthropic | **顶层字段** | **扁平 `input_schema`** | user 消息里的 `tool_use_id` 块 |
| OpenAI | messages 首元素 | `function.parameters` | `role:"tool"` + `tool_call_id` |

另外 OpenAI 的 `arguments` 是**序列化字符串**（`call.args.dump()`），
Ollama 是 object。

**选项**

- A 抽一个「请求构建器」基类，用虚函数覆盖差异点。
- B 三个 `.cpp` 各写一遍。

**选择 B。理由**：差异点是 3×3 的，共同点只剩「都要 POST 一个 JSON」。
抽基类会得到一个每个方法都被覆盖的基类 —— 那不是抽象，是仪式。
三份直白的代码更容易对照 wire 文档核对。

**代价**：加第四个 provider 要再写一遍。但真正的成本从来不在打字，
而在读懂对方的 wire 格式。

**可迁移的一般原则**：抽象要抽**共同点**，不是抽**位置**。
如果一个基类的每个虚函数都会被每个子类覆盖，那它没有承载任何共享逻辑。
先数一数真正共享的行数。

### 决策 12：SSE 分帧抽成共享 seam，累积不抽

Anthropic 和 OpenAI 的**分帧规则完全一致**（空行是事件边界、多行 `data` 用 `\n`
拼接、`:` 前缀是心跳注释、CRLF 要剥、未收尾的尾帧要扣住），所以
`provider/sse.hpp` 的 `FrameAssembler` 两者共用。

但**累积**逻辑不共享（见决策 10）。

**可迁移的一般原则**：同一组适配器里，共享的边界要划在**逐行核对过的相同规则**
上，而不是划在「看起来都是 SSE」这种粗粒度相似性上。分帧相同、语义不同，
就只共享分帧。

## 四、Agent 语义：记忆与技能

### 决策 13：记忆用 JSONL，不用单个 JSON 文档

**选项**

- A 单个 JSON 数组，读-改-写整个文件。
- B JSONL，一条记录一行。

**选择 B**，三个理由各自独立：

1. 追加一条就是 append 写 `<record>\n`，不需要读-改-写。
2. 按行可寻址：`forget` 剔掉命中的行、重写存活的行；**坏行只影响它自己**。
3. grep 友好 —— 人要审计 agent 存了什么关于自己的事实时，直接看得懂。

第 3 点是选它的主要动机，而它反过来**决定了第 2 点必须成立**：既然预期人会手工
编辑这个文件，那么一次手滑不能让全部记忆不可用。所以加载时坏行（JSON 解析失败 /
非对象 / scope 非法 / id 空 / text 空）静默跳过续读。

**代价**：`forget` 是 O(n) 重写。在这个量级完全可忽略。

**可迁移的一般原则**：选存储格式时，把「**谁会手工看它、手工改它**」当成一等约束。
这个约束一旦成立，就会连带决定容错策略 —— 二者不能分开考虑。

### 决策 14：project scope 不可用时报错，而不是回退到 user

**这是 memory 模块最重要的一条决定。**

**问题**：`remember` 要写 project 记忆，但当前没有可写的工作区根。

**选项**

- A 静默回退到 user scope。实现最简单，「至少存下来了」。
- B 报错，并在错误信息里说明如何显式声明全局事实。

**选择 B。理由**：一条 project 事实被提升到 user scope，会加载进**每一个**其他
工作区的系统提示 —— 在项目 B 工作时看到关于项目 A 的事实。这种「跨工作区记忆
串味」很难被发现，因为它不报错，只是慢慢让提示变脏。

```cpp
if (scope == Scope::Project) {
    result.error = "remember: project scope is unavailable here (no writable "
        "workspace root), so there is nowhere to store a project-scoped fact. "
        "Pass scope=\"user\" if you meant a global fact that loads into every "
        "workspace.";
}
```

**代价**：模型多一次往返。可接受 —— 错误信息里直接给了 `scope="user"` 这条出路，
模型能一次纠正。

同理，`remember` 的 scope **缺省是 project**：写错了只影响当前工作区，
而默认全局会污染每一个其他工作区。默认值要选**错误后果较小**的那个。

**可迁移的一般原则**：当「猜错」的后果是**污染全局状态**时，宁可失败并说明，
不要静默降级。降级的诱惑在于「至少完成了」，但污染全局状态的代价是持续的、
且难以追溯来源。

### 决策 15：roots 注入，不在类内部读环境

`MemoryStore` 和 `SkillEngine` 都接收注入的根路径，`discover_roots()` 是唯一
碰环境的函数。这与仓库既有的 `make_read_tool(workspace_root)` 是同一个约定。

**收益**：全部纯逻辑（解析、覆盖、重写、渲染）可以喂临时目录测，
不需要改 `$HOME`、不需要 chdir、测试之间零耦合。

**可迁移的一般原则**：「读环境」和「用环境值做事」是两件事，拆开。
拆开的那一刀就是测试的接入点，而且这个接入点是免费的 —— 不需要 mock 框架、
不需要依赖注入容器，只是一个构造参数。

### 决策 16：skill 三层渐进披露的动机是上下文预算，不是优雅

**问题**：skill 是指令文档，怎么让模型用上。

**选项**

- A 全部正文都放进系统提示。
- B 三层：目录常驻 / 正文按需 / 资源只列不读。

**选择 B。理由是可以算的**：把所有正文放进提示，token 随 skill 数量**线性增长**，
而任一回合真正用得上的通常**只有一份**。这台机器上 `~/.claude/skills/` 里有
十几份 skill，全放进去是几万 token 的常驻成本，命中率不到 10%。

三层的分界：

| 层 | 内容 | 何时加载 | 成本 |
|---|---|---|---|
| Tier1 | 名字 + 一句描述 | 每轮常驻 | 每份约 20 token |
| Tier2 | SKILL.md 正文 | 模型调 `skill` 工具 | 一次一份 |
| Tier3 | 附带资源文件 | 模型调 `read` | 按需，可能永不 |

**每一层都有一个防误用的措辞**，这些不是装饰：

- Tier1 块里写「load it rather than guessing what it says」——
  只给一句描述时，模型会照着描述**编造**正文内容。
- Tier2 payload 里给 skill 目录的**绝对路径** ——
  正文里的相对路径是相对 skill 目录的，而工具的 cwd 是工作区，不给绝对路径拼不出来。
- Tier3 清单后面写「These files are NOT loaded」——
  防止模型假设内容已经在手上。

**代价**：多两次往返（activate + read）。换来的是常驻成本从 O(n) 降到 O(1)。

**可迁移的一般原则**：分层加载的层数不该由「看起来几层合适」决定，
而由**成本曲线**决定：哪些内容的成本随规模增长、命中率又低，就是该往后推的那一层。

### 决策 17：frontmatter 按第一个冒号切，不用 YAML 库

**问题**：`description: Use when: handling PDFs` 这种未加引号的冒号怎么处理。

**选项**

- A 引入 YAML 库，严格解析。
- B 手写迷你解析器，按**第一个**冒号切。

**选择 B。理由**：这种写法在真实 skill 里很常见，别的客户端也接受。
严格 YAML 会拒掉整行 —— 而我们的目标之一就是能读**别人已经装好的** skill
（`.claude/skills` 兼容）。为了规范正确性而读不了真实数据，是本末倒置。

配套的宽容策略：陌生键跳过（`allowed-tools` / `license` 是别的客户端写的）、
缺 `name` 回退目录名、缺 `description` 回退正文首个非空行、
完全没有 frontmatter 则整份当正文（手写 skill 常这样，不是损坏文件）。

**代价**：不支持块标量等 YAML 高级语法。真实 skill 里用不到。

**可迁移的一般原则**：解析**别人生产的**数据时，宽容度比规范正确性重要。
先确认真实样本长什么样，再决定严格程度 —— 而不是先选库再抱怨数据不合规。

### 决策 18：不缓存 skill 发现结果

**选项**

- A 缓存，用所有根 + 所有 SKILL.md 的 mtime 拼成 key 做失效。
- B 每次重扫。

**选择 B。理由**：目录扫描在这个量级可忽略，而正确的缓存要跟 mtime，
那是一整套失效逻辑（新增文件、删除文件、根目录本身变化）。
手工新增一个 skill 下一轮就该出现在目录里，这个语义比省下几毫秒重要。

**可迁移的一般原则**：加缓存前先量成本。缓存的真实代价不是内存，
是**失效逻辑的正确性**，而那部分复杂度会一直留在代码里。

## 五、安全边界

### 决策 19：读允许列表只放宽读，且只在 workspace 检查失败后才查

**问题**：Tier3 要读 skill 附带的资源，但 skill 常装在 `$HOME` 下，
完全在工作区外，会撞上 `read` 的硬边界。

**选项**

- A 去掉 workspace 边界，改成黑名单。
- B 把 workspace 换成「workspace ∪ skill 目录」的白名单，读写都放宽。
- C 白名单**只对读生效**，且只在 workspace 检查失败后才查。

**选择 C**。三个约束各有理由：

1. **只放宽读**：一个装在 `$HOME` 的 skill 目录可读，**不意味着** agent 可以往
   那里写。列表不参与任何写入判断。
2. **顺序在后**：workspace 命中就直接返回，允许列表只是「额外的例外」，
   不改变主路径的语义。
3. **保留硬边界**：不在列表里、也不在 workspace 里的路径照旧拒绝。

```cpp
if (is_within_workspace(workspace_root, target)) {
    return target;
}
// 允许列表只在这里参与判断，且只对读生效。
for (const fs::path& allowed : allowed_roots) {
    if (is_within_workspace(allowed, target)) {
        return target;
    }
}
return std::unexpected(ToolError{.kind = ErrorKind::OutOfWorkspace, ...});
```

**验证方式值得单独说**：单元测试故意把 workspace 指向一个**与 skill 根无关的空
目录**，这样允许列表是唯一能让读通过的途径 —— 测试不会被「文件碰巧在工作区内」
蒙混过去。端到端再验一次反方向：`/etc/hostname` 和 `~/.bashrc` 仍然被拒。

**可迁移的一般原则**：放宽一个安全边界时，把放宽的**维度**（只读不写）、
**顺序**（例外在主判断之后）、**范围**（具体路径而非通配）三件事分别写清楚。
并且测试要构造成「不放宽就必然失败」，否则测试通过说明不了任何事。

### 决策 20：`effects` 必须如实描述工具行为

**问题**：`remember` / `forget` 写文件。计划里写的是 `EffectSet{}`（纯，不需审批）。

**选择**：改成 `{Effect::WriteFs}`，**偏离了计划**。

**理由**：`effects` 是权限系统的**唯一输入**。把写文件的工具标成纯的，
整个 policy 层就失去可信度 —— 用户看到「这个工具是纯的」却发现它改了磁盘，
之后就不会再信任任何 effect 声明。

**代价**：零。默认 `write` profile 下 policy 一律 Allow，演示路径不受影响；
而 `ask` / `minimal` 下用户才**真的**能管住 agent 往磁盘上记了什么。

同理 `skill` 工具声明 `ReadFs` 而不是 `WriteFs` —— activate 只读 SKILL.md。
如实的意思是两个方向都如实，不夸大也不缩小。

**可迁移的一般原则**：元数据（权限声明、能力标注、类型标记）一旦有一处说谎，
依赖它的整套机制就都不可信了。「反正当前配置下不检查」不是放松的理由 ——
那正是它日后被信任却出错的路径。

## 六、测试策略

### 决策 21：破坏验证（sabotage）—— 确认测试真的在鉴别行为

写完一组测试后，**故意改坏实现**，确认失败的恰好是对应的那个测试。
这轮做了四次，每次都是一行改动 + 一次 `cp /tmp/x.bak` 还原：

| 破坏 | 预期失败 | 结果 |
|---|---|---|
| 去掉 SSE 的 CR 剥离 | CRLF 测试 | ✅ 恰好 1 个 |
| OpenAI `tools_[index]` → `tools_[0]` | 交错累积测试 | ✅ 恰好 1 个 |
| memory 注入 project→user 回退 | 无串味测试 | ✅ 恰好 1 个 |
| skill 根顺序反转 | project 覆盖测试 | ✅ 恰好 1 个 |
| 允许列表包含判断 → `if (true)` | 边界测试 | ✅ 恰好 1 个 |

**为什么值得做**：全绿的测试有两种，一种是「实现正确」，一种是
「测试根本没在鉴别」。第二种在写完的当下无法区分，破坏验证是唯一的区分手段。
成本极低（一行改动），而它证明的东西是：这个断言**能够**失败。

「恰好 1 个失败」还额外证明了测试之间没有意外耦合。

**可迁移的一般原则**：新写的测试全绿时，破坏一次实现确认它会红。
写不出「怎么改坏能让它失败」的测试，说明那个测试没有鉴别力。

### 决策 22：端到端验证不可跳过 —— 三次实测缺陷为证

**单元测试全绿不等于功能可用。** 这轮有三次实测证据：

**（1）流式下 `remember` 完全不被调用**

单元测试全绿，但 REPL 里模型只在散文里答应「已记下」然后什么也不调，事实全丢。

诊断过程（逐个变量隔离，不是猜）：
1. dump 真实请求体 → `TOOLS: [calculator, read, remember, forget]`，接线正确
2. 非流式 curl → 模型**确实**调了 `remember`
3. 流式 + 字节相同的请求体 → 只有散文
4. 只把 `stream` 翻成 `false` → 工具调用出现，**隔离出唯一变量**
5. 但 `read` 在流式下是好的（切片 4 集成测试通过），所以不是流式本身的问题
6. 推断：既有指引「工具能更可靠回答问题时就用工具」**覆盖不到** `remember`
   —— 它不回答任何问题
7. 流式 + 加一条记忆指引 → 工具调用出现，**先确认假设再改生产代码**

**（2）`forget` 零命中被读成成功**

模型说「已删除」，磁盘上记录还在。提示里明明有 `[55f091af] User prefers fish shell`，
模型传的是 `text: "shell preference"` —— 严格子串零命中，工具回报
`"forgot 0 memory record(s)"`，模型把它读成成功。

这是**工具输出措辞的设计缺陷**，不是模型的错。任何单元测试都不会注意到
「这句话会被误读」。修法是让措辞说明什么都没变，并指回 id 这条可靠路径；
schema 里直接举反例说明 `text` 是字面子串而非描述。

**（3）测试辅助函数返回悬垂引用**

`find_tool` 返回指向 `make_skill_tools(...)` 临时 vector 的引用，
整个表达式结束就悬垂，直接 segfault，编译期无警告。
用 `gdb -batch -ex run -ex bt` 一次拿到栈，比逐行加打印快得多。

**验证多层结构的方法**：给每层埋**只在该层出现的哨兵字符串**。
skill 三层用了 `ostrich-lantern-42`（只在 SKILL.md）和
`marmalade-vault-77`（只在 references/tone.md），从输出就能判断哪几层真的生效，
不靠推测。再把 skill 装到工作区外重跑一次，Tier3 才真正依赖允许列表。

**可迁移的一般原则**：LLM 相关功能，单元测试只能证明「代码按我想的执行」，
不能证明「模型会按预期使用它」。后者只有真跑才知道。
抓到缺陷后**先写 Red 锁住**再改 —— 这类缺陷最容易在日后重排提示时静默复发。

### 决策 23：集成测试在依赖不可达时 skip，不 fail

Ollama 集成测试开头探测 `localhost:11434`，不可达就 `GTEST_SKIP()`。

**理由**：这类测试的价值在于「有环境时提供真实信号」，
而不是「强制每个人都装 Ollama」。fail 会让 CI 和新克隆的仓库变红，
红久了就没人看红了。

**可迁移的一般原则**：依赖外部服务的测试，缺依赖时 skip。
一个长期红着的测试比没有测试更糟 —— 它训练团队忽略红色。

### 决策 24：垂直切片，一个 seam 一个测试一次最小实现

八个切片每个都是一颗 tracer bullet：切片 4 打通「HTTP + 行分帧 + Msg 映射」
就立刻端到端跑真实模型，而不是先把三个 provider 都写完再联调。

反面教训在这轮内部也出现过：写 `parse_skill` 时我一次写了六个测试再实现，
属于**横向切片**。虽然结果正确，但那六个测试验证的是「我想象中的行为形状」，
而不是逐个被实现推着长出来的。补救办法是做破坏验证 —— 事后确认它们有鉴别力。

**可迁移的一般原则**：一次一个 seam。批量写测试会让你在理解实现之前就锁定测试
结构，而测试结构一旦定下来很少有人回去改。

## 七、被拒绝的方案

上面每条决策里的「选项 A」都是被拒绝的那个。集中列一遍，因为**被拒绝的方案往往
比被选中的更能说明判断依据** —— 它们都是当时看起来合理、甚至更"标准"的做法。

### 实现层面

| 被拒方案 | 看起来为什么合理 | 真正的问题 |
|---|---|---|
| `update()` 里直接读文件填系统提示 | 最直观，少一个注入点 | 核心失去纯性，确定性测试要背文件系统夹具 |
| 系统提示当 `Model` 字段 | 状态集中，看起来干净 | Model 每轮都不同，快照比较失去意义 |
| `in_flight_` 计数器 | 教科书写法，语义直白 | 与 `phase` 冗余，不一致就是最难查的 bug |
| `std::binary_semaphore` 做唤醒 | 合并语义正确，代码最短 | 已置起时 `release()` 是 UB，而那是这里的常态 |
| 先 wait 再 drain | 逻辑上"等到有事再处理" | 「消息已入队但唤醒已被消费」的窗口会挂死 |
| 析构时 join 隔离线程 | 不泄漏线程，教科书答案 | 任务 wedge 时 `~AsyncHost` 永久挂死 —— 毁掉隔离的目的 |
| 先接 Anthropic（最难的） | "先攻难点" | 第一颗子弹要同时验证四件事，失败无从定位 |
| `Msg` 加 `StreamToolCallDelta` | 让 Core 统一拼装 | Core 为迁就两个 provider 变得比任一个都复杂 |
| `unordered_map<int, ToolAccumulator>` | 查找更快，反正会全遍历 | 遍历顺序就是输出的一部分，测试变 flaky |
| 请求构建器基类 + 虚函数 | 消除三份"重复" | 3×3 全是差异点，每个虚函数都被覆盖 = 仪式 |
| 单个 JSON 文档存记忆 | 结构完整，一次解析 | 一处手滑坏掉整个文件；不能 append |
| project scope 不可用时回退 user | "至少存下来了" | 跨工作区记忆串味，不报错、只慢慢污染 |
| 全部 skill 正文进提示 | 一次到位，无往返 | 常驻成本 O(n)，命中率不到 10% |
| 引入 YAML 库严格解析 | 规范正确 | 读不了别人已装好的真实 skill —— 本末倒置 |
| 缓存 skill 发现结果 | 省掉目录扫描 | 失效逻辑（mtime × 增删 × 根变化）的复杂度永久留在代码里 |
| `remember`/`forget` 标 `EffectSet{}` | 计划里这么写的，当前配置也不检查 | 元数据说谎一次，整套权限机制不可信 |
| 去掉 read 的 workspace 边界改黑名单 | 一次解决所有路径问题 | 把硬边界换成软边界，Tier3 的需求不值这个代价 |
| 允许列表读写都放宽 | 对称，实现更少分支 | 可读 ≠ 可写；`$HOME` 下的 skill 目录不该被写 |

### 范围层面（本轮明确不做）

这些不是"没时间做"，是**判断当前不做更好**：

- **RAG / 向量检索**：memory 的当前量级用不上；引入 embedding 依赖会把项目重心
  从「运行时架构」拖到「检索质量」，而后者不是这条线要展示的东西。
- **真实 Anthropic / OpenAI 网络测试**：需要付费 key，且 CI 里必然 skip。
  两者只保证编译 + SSE 分帧/累积的单元测试，真实信号全部由本地 Ollama 提供。
- **HTTP/2、自写 TLS**：借 cpp-httplib + OpenSSL。手写 TLS 是另一个项目。
- **正式 TUI 渲染层**：留作独立工作。**这里有一条要如实说明的话** ——
  当初把 `Printer` 说成"未来 TUI 的干净扩展点"，但它只读 `messages.back()`
  并按已打印长度追加，真正的 TUI 需要从 `model()` 做**全帧投影**。
  所以那个扩展点只是名义上干净，不是现成的。

**可迁移的一般原则**：写"扩展点"三个字时要自检一遍 —— 是真的接上就能用，
还是只是位置留对了。名义上的扩展点会在日后被当成已完成的工作，那是最贵的一类
乐观估计。

## 附录：可迁移原则速查

脱离本项目上下文的版本。1~24 对应上面 24 条决策，第 25 条来自第七节。

**纯核心与边界**

1. 需要 IO 的数据不塞进纯函数、也不塞进状态，做成**在效果边界求值的函数** ——
   副产品是「每次都拿到最新值」免费到手。
2. 给聚合体加字段前，先确认既有构造点用的是 designated initializer 还是位置
   初始化。前者能无痛加字段，后者不能。

**并发**

3. 用既有状态代替冗余计数器的前提是**把它依赖的不变量显式强制出来**。
   「这个契约靠谁保证」必须有答案，且答案不能是「大家小心一点」。
4. 合并型唤醒必须配「先检查后等待」的循环。反着写在低负载下也能跑，
   只在竞态窗口命中时挂死。
5. 选并发原语时确认**你的常态调用序列**在该原语定义域内。「语义对得上」
   不等于「用法合法」。
6. 「不泄漏资源」不是最高优先级。当严格清理会导致**更严重**的失败模式时，
   选可控的泄漏 + 共享所有权消掉悬垂。先问「哪个失败更糟」。
7. 容器里的对象被外部持有指针时，`reserve` 从性能优化升级成正确性前提 ——
   必须写进注释，否则会被「顺手清理」掉。

**适配器与抽象**

8. 多个同类适配器，先做**能力最原子、反馈最快**的那个跑通端到端，
   再用第二个检验抽象。
9. 适配器之间的差异要在**最靠外的那一层**吸收掉。让核心迁就多个外部格式，
   结果是核心比任何一个都复杂。
10. 需要确定性输出时用有序容器。「反正会全部遍历」不是理由 ——
    遍历顺序本身就是输出的一部分。
11. 抽象要抽**共同点**，不是抽**位置**。每个虚函数都被每个子类覆盖的基类
    没有承载任何共享逻辑。先数真正共享的行数。
12. 共享边界要划在**逐行核对过的相同规则**上，不是划在「看起来都是 SSE」
    这种粗粒度相似性上。

**存储与 Agent 语义**

13. 选存储格式时把「**谁会手工看它、手工改它**」当成一等约束 ——
    这个约束会连带决定容错策略，二者不能分开考虑。
14. 当「猜错」的后果是**污染全局状态**时，宁可失败并说明，不要静默降级。
    默认值要选**错误后果较小**的那个。
15. 「读环境」和「用环境值做事」拆开。那一刀就是测试接入点，
    而且免费 —— 只是一个构造参数。
16. 分层加载的层数由**成本曲线**决定：成本随规模增长、命中率又低的内容，
    就是该往后推的那一层。
17. 解析**别人生产的**数据时，宽容度比规范正确性重要。先看真实样本长什么样，
    再决定严格程度。
18. 加缓存前先量成本。缓存的真实代价不是内存，是**失效逻辑的正确性**，
    而那部分复杂度会一直留在代码里。

**安全**

19. 放宽安全边界时，把**维度**（只读不写）、**顺序**（例外在主判断之后）、
    **范围**（具体路径而非通配）分别写清楚。测试要构造成「不放宽就必然失败」。
20. 元数据一旦有一处说谎，依赖它的整套机制都不可信。「反正当前配置下不检查」
    正是它日后被信任却出错的路径。

**测试**

21. 新写的测试全绿时，破坏一次实现确认它会红。写不出「怎么改坏能让它失败」
    的测试，说明它没有鉴别力。
22. LLM 相关功能，单元测试只能证明「代码按我想的执行」，不能证明「模型会按预期
    使用它」。抓到缺陷后先写 Red 锁住再改。
23. 依赖外部服务的测试缺依赖时 skip。长期红着的测试比没有测试更糟 ——
    它训练团队忽略红色。
24. 一次一个 seam。批量写测试会在理解实现之前锁定测试结构，
    而测试结构定下来后很少有人回去改。

**关于「扩展点」**

25. 写「扩展点」三个字时自检：是接上就能用，还是只是位置留对了。
    名义上的扩展点会被当成已完成的工作。
